# 智维先知 — 模型选型与本地部署方案

> 基于 Ollama 本地部署，适配 6-Agent 多专家架构

---

## 一、核心策略：3模型按职责路由

不是所有Agent都需要最大模型。关键是用**对的模型做对的事**。

| 模型 | 参数量 | 显存占用 | 职责 | 为什么选它 |
|------|--------|----------|------|-----------|
| `qwen2.5:14b` | 14B | ~10GB | 深度推理 | ReAct循环需要多步推理，14B在推理深度和速度间平衡最好 |
| `qwen2.5:7b` | 7B | ~5GB | 快速响应 | Monitor 24/7轮询，需要低延迟；Knowledge/Reflection任务简单 |
| `bge-m3` | 568M | ~2GB | 向量嵌入 | 中文语义理解强，1024维，支持稠密+稀疏+多向量检索 |

**总显存：~17GB（3模型并行）**

## 二、6个Agent的模型分配

### 需要深度推理的（用 14b）

| Agent | 为什么需要14b | 关键能力 |
|-------|--------------|---------|
| **Diagnostic** | ReAct循环需要：观察异常→假设根因→调用工具验证→修正假设→输出证据链 | 多步推理 + 工具调用 + 结构化输出 |
| **Decision** | What-if分析需要：评估减载方案→计算成本收益→推荐维护窗口→规划资源 | 前向推演 + 多方案对比 |
| **Prediction** | 需理解RUL分布含义，解释P10/P50/P90，给出置信度判断 | 统计理解 + 概率推理 |
| **Report** | 需要结构化生成完整诊断报告，语言质量要求高 | 长文本生成 + 专业术语 |

### 只需快速响应的（用 7b）

| Agent | 为什么7b够用 | 关键能力 |
|-------|-------------|---------|
| **Monitor** | 24/7轮询，每秒处理传感器流，只需判断"是否异常"，不需要复杂推理 | 分类 + 数值比较 |
| **Knowledge** | 向量检索+结果摘要，不需要复杂推理，7b的摘要能力足够 | 检索 + 摘要 |
| **Reflection** | 5项Checklist自检，格式固定，7b完全胜任 | 模板填充 + 判断 |

### 非生成式（用 bge-m3）

| 用途 | 说明 |
|------|------|
| ChromaDB向量索引 | 对设备手册、案例库、维护SOP做向量化 |
| 案例语义匹配 | 输入异常描述→检索历史相似案例 |
| 知识库RAG检索 | 诊断Agent检索相关FMECA条目 |

## 三、Ollama 安装与配置

### 3.1 拉取模型

```bash
# 深度推理模型（主力）
ollama pull qwen2.5:14b

# 快速响应模型（监控+轻量任务）
ollama pull qwen2.5:7b

# 向量嵌入模型
ollama pull bge-m3

# 可选：如果显存充裕（24GB+），可额外拉取
# ollama pull qwen2.5:32b   # 极致推理，但速度慢
```

### 3.2 Ollama 服务配置

创建 `/etc/systemd/system/ollama.service` 或 Windows 下的环境变量：

```bash
# Linux: /etc/systemd/system/ollama.service
Environment="OLLAMA_HOST=0.0.0.0:11434"
Environment="OLLAMA_MAX_LOADED_MODELS=3"
Environment="OLLAMA_NUM_PARALLEL=2"
Environment="OLLAMA_KEEP_ALIVE=30m"
```

Windows 下设置环境变量：
```powershell
# PowerShell（管理员）
[System.Environment]::SetEnvironmentVariable("OLLAMA_HOST", "0.0.0.0:11434", "Machine")
[System.Environment]::SetEnvironmentVariable("OLLAMA_MAX_LOADED_MODELS", "3", "Machine")
[System.Environment]::SetEnvironmentVariable("OLLAMA_NUM_PARALLEL", "2", "Machine")
[System.Environment]::SetEnvironmentVariable("OLLAMA_KEEP_ALIVE", "30m", "Machine")
```

参数说明：
- `OLLAMA_MAX_LOADED_MODELS=3` — 允许3个模型同时驻留显存（14b+7b+bge-m3）
- `OLLAMA_NUM_PARALLEL=2` — 允许2个并发请求（Monitor和Diagnostic可能同时跑）
- `OLLAMA_KEEP_ALIVE=30m` — 模型加载后保持30分钟，避免频繁卸载

## 四、每个Agent的模型参数配置

温度（temperature）是核心参数——不同任务需要不同的"创造性"：

| Agent | 模型 | temperature | top_p | max_tokens | num_ctx | 为什么 |
|-------|------|-------------|-------|------------|---------|--------|
| Monitor | 7b | **0.1** | 0.9 | 512 | 4096 | 分类任务，需要确定性输出，低温 |
| Diagnostic | 14b | **0.3** | 0.85 | 2048 | 8192 | 推理需要一点发散但不能幻觉，中低温 |
| Prediction | 14b | **0.2** | 0.9 | 1024 | 8192 | 统计解释需精确，低温 |
| Decision | 14b | **0.4** | 0.85 | 2048 | 8192 | 方案探索需要一些发散，中温 |
| Knowledge | 7b | **0.1** | 0.9 | 1024 | 4096 | 检索摘要需忠实原文，极低温 |
| Report | 14b | **0.5** | 0.9 | 4096 | 8192 | 报告生成需要流畅表达，中高温 |
| Reflection | 7b | **0.0** | 0.9 | 512 | 4096 | 自检必须严格确定性，温度0 |

    "knowledge":  ModelConfig(ModelName.QWEN_7B,  0.1, 0.9, 1024, 4096),
    "report":     ModelConfig(ModelName.QWEN_14B, 0.5, 0.9, 4096, 8192),

### 5.2 Ollama客户端封装

```python
# src/llm/ollama_client.py

import httpx
from typing import Optional
from config.model_config import ModelConfig


class OllamaClient:
    """Ollama API 客户端，兼容 OpenAI 接口风格"""

    def __init__(self, base_url: str = "http://localhost:11434"):
        self.base_url = base_url
        self.client = httpx.AsyncClient(
            base_url=base_url,
            timeout=httpx.Timeout(120.0, connect=10.0)
        )

    async def chat(
        self,
        messages: list[dict],
        config: ModelConfig,
        tools: Optional[list[dict]] = None,
        stream: bool = False
    ) -> dict:
        """对话接口，支持工具调用"""
        payload = {
            "model": config.model,
            "messages": messages,
            "stream": stream,
            "options": {
                "temperature": config.temperature,
                "top_p": config.top_p,
                "num_predict": config.max_tokens,
                "num_ctx": config.num_ctx,
            },
            "keep_alive": config.keep_alive,
        }
        if tools:
            payload["tools"] = tools

        response = await self.client.post("/api/chat", json=payload)
        response.raise_for_status()
        return response.json()

    async def embed(
        self,
        text: str,
        model: str = "bge-m3"
    ) -> list[float]:
        """向量嵌入接口"""
        payload = {"model": model, "prompt": text}
        response = await self.client.post("/api/embeddings", json=payload)
        response.raise_for_status()
        return response.json()["embedding"]

    async def health_check(self) -> bool:
        """健康检查"""
        try:
            resp = await self.client.get("/api/tags")
            return resp.status_code == 200
        except Exception:
            return False
```

## 六、每个Agent的System Prompt要点

不同模型能力不同，Prompt策略也不同：

### Monitor（7b — 简单分类）

```text
你是CNC设备健康监控Agent。你的职责是判断设备是否异常。

输入：18维传感器实时读数 + 24小时滑动窗口统计量
输出：JSON格式的健康评分和异常标记

判断规则：
- 温度 > 75°C → 异常
- 振动RMS > 4.5mm/s → 异常
- 电流偏差 > 额定值15% → 异常
- 健康评分 = 1 - (异常维度数 / 18)

只输出JSON，不要解释。
```

7b模型不需要复杂推理，用**规则驱动 + 结构化输出**。

### Diagnostic（14b — ReAct多步推理）

```text
你是CNC设备故障诊断Agent。使用ReAct模式推理。

收到异常告警后，按以下步骤推理：

Thought: 分析当前异常模式（哪些维度异常、趋势如何、突变还是渐变）
Action: 调用工具查询历史趋势 [tool: query_trend]
Observation: [工具返回的趋势数据]
Thought: 根据趋势判断可能的故障模式（渐变=磨损退化，突变=突发故障）
Action: 调用工具检索相似历史案例 [tool: case_search]
Observation: [工具返回的案例]
Thought: 结合趋势和案例，形成根因假设
Action: 调用工具查询FMECA知识库验证假设 [tool: fmeca_lookup]
Observation: [知识库返回的故障模式-原因-后果]
Thought: 构建诊断证据链 E1→E2→E3→E4→E5→E6→E7
Action: 输出最终诊断报告 [tool: output]

置信度低于70%时，重新推理（最多3轮）。

输出格式：
{
  "fault_mode": "故障模式名称",
  "root_cause": "根因分析",
  "evidence_chain": ["E1...", "E2...", ...],
  "confidence": 0.85,
  "severity": "warning|critical|emergency"
}
```

14b模型需要**结构化推理框架 + 工具调用 + 置信度自检**。

### Decision（14b — What-if规划）

```text
你是CNC设备维护决策Agent。你的职责是给出最优维护方案。

输入：故障诊断结果 + RUL预测 + 设备元数据 + 生产排程
输出：维护决策方案

决策维度：
1. 维护时机：立即停机 / 减载运行至下次计划停机 / 延至维护窗口
2. 维护类型：更换部件 / 修复调整 / 状态监控加密
3. 资源调度：维修人员、备件、工具
4. 成本分析：停机损失 vs 维护成本 vs 风险成本

对每个方案给出：
- 预期RUL延长（小时）
- 停机时长（小时）
- 直接成本（元）
- 风险成本 = 故障概率 × 故障后果成本
- 净收益 = 延长RUL价值 - 总成本

推荐净收益最高的方案。
```

## 七、显存管理与并发策略

### 7.1 模型加载策略

Ollama默认行为是模型空闲后自动卸载。对于你的系统：

| 模型 | 加载策略 | 原因 |
|------|---------|------|
| 7b | **常驻显存**（keep_alive=30m） | Monitor 24/7轮询，不能等加载 |
| 14b | **按需加载**（keep_alive=10m） | 不是每秒都在推理，10分钟空闲后卸载 |
| bge-m3 | **常驻显存**（keep_alive=30m） | 每次诊断都要检索，频繁加载太慢 |

### 7.2 并发控制

```python
# src/llm/concurrency.py

import asyncio
from contextlib import asynccontextmanager


class ModelSemaphore:
    """控制每个模型的并发请求数"""

    def __init__(self):
        self._semaphores = {
            "qwen2.5:14b": asyncio.Semaphore(2),   # 14b最多2并发
            "qwen2.5:7b": asyncio.Semaphore(4),     # 7b轻量，允许4并发
            "bge-m3": asyncio.Semaphore(8),         # 嵌入很快，允许8并发
        }

    @asynccontextmanager
    async def acquire(self, model: str):
        sem = self._semaphores.get(model)
        if sem:
            async with sem:
                yield
        else:
            yield
```

### 7.3 队列优先级

```python
# 诊断循环中，Diagnostic和Decision可能同时请求14b
# 设置优先级：Diagnostic > Decision > Report

PRIORITY_ORDER = {
    "diagnostic": 1,   # 最高，实时诊断
    "decision": 2,     # 次高，决策建议
    "prediction": 3,   # 中等
    "report": 4,       # 最低，报告生成可以等
}
```

## 十一、关键注意事项

### 11.1 Ollama Function Calling 限制

Ollama从0.3.0开始支持function calling，但Qwen2.5的function calling能力弱于GPT-4。**建议用结构化Prompt替代function calling**：

```python
# 不推荐：依赖Ollama原生function calling
tools = [{"type": "function", "function": {"name": "query_trend", ...}}]

# 推荐：用结构化Prompt引导模型输出工具调用
system_prompt = """
你可以调用以下工具：
1. query_trend(machine_id, sensor, hours) — 查询历史趋势
2. case_search(description, top_k) — 检索历史案例
3. fmeca_lookup(fault_mode) — 查询FMECA知识库

需要调用工具时，输出JSON：
{"tool": "query_trend", "args": {"machine_id": "CNC_002", "sensor": "spindle_temp", "hours": 24}}
"""
```

LangGraph的 `ToolNode` 和 `tool_calls` 解析需要适配这种JSON输出模式。

### 11.2 上下文窗口管理

14b模型 `num_ctx=8192` 约支持6000字中文。诊断循环中历史信息会累积，需要：

```python
# 超过上下文限制时自动压缩
MAX_CONTEXT_MESSAGES = 20  # ReAct循环中最多保留20条消息

if len(messages) > MAX_CONTEXT_MESSAGES:
    # 保留system + 前3条 + 后10条，中间用摘要替代
    summary = await summarize_history(messages[3:-10])
    messages = [messages[0]] + [{"role": "system", "content": summary}] + messages[-10:]
```

### 11.3 嵌入模型选型对比

| 模型 | 维度 | 中文能力 | 速度 | 显存 | 推荐度 |
|------|------|---------|------|------|--------|
| **bge-m3** | 1024 | 优秀 | 中 | 2GB | 首选 |
| bge-large-zh | 1024 | 优秀 | 中 | 1.3GB | 备选 |
| nomic-embed-text | 768 | 一般 | 快 | 0.5GB | 英文场景 |
| qwen2.5-embed | 1024 | 优秀 | 中 | 1.5GB | 需手动安装 |

**推荐bge-m3**：支持稠密+稀疏+多向量三种检索模式，且对中文工业术语理解好。

## 十二、总结决策树

```
你的显卡显存 >= 24GB?
├─ 是 → 方案1: 14b + 7b + bge-m3 三模型并行（推荐）
│        总显存17GB，余量充足
│
├─ 16-24GB → 方案2: 14b-q4 + 7b-q4 + bge-m3（量化版）
│           总显存14GB，质量略降但可用
│
├─ 8-16GB → 方案3: 仅7b + bge-m3
│          降级方案A，Diagnostic质量降但跑得动
│
└─ < 8GB → 方案4: 仅7b（嵌入也用7b的hidden state）
           或方案B: 本地7b + 云端API混合
```

**如果不确定，先从方案1开始。14b的推理深度对诊断质量影响很大——ReAct多步推理在7b上经常断裂（第2步就忘了第1步的结论）。**
