# 企业级预测性维护Agent：数据集与知识库建设战略规划

> 本文档回答三个核心问题：
> 1. 当前数据集有什么问题？企业级数据集应该长什么样？
> 2. 知识库怎么从"文本文件"升级为"可推理的知识系统"？
> 3. Agent应该从"对话水平"进化到什么程度？要不要模拟数据？

## 一、当前数据集问题诊断（回顾与深化）

### 1.1 你现在有什么

| 数据文件 | 内容 | 行数 | 问题 |
|----------|------|------|------|
| MACHINE_LOG_DATA._2025.csv | 时序传感器数据 | 3000 | ~7小时，每14分钟采样1次，仅4个传感器维度 |
| MACHINE_SUMMARY_DATA._2025.csv | 设备元数据 | ~100 | 结构合理但信息量少 |
| PRODUCT_ASSEMBLY_LINE_WITH_MACHINES_TESTS_2025.csv | 质量测试参数 | ~数百 | 测试对象是PCB电子元件，与CNC加工质量无关 |
| PRODUCT_ASSEMBLY_LINE_WITH_MACHINES_2025.csv | 质量测试汇总 | ~数十 | 同上，数据类型不匹配 |
| 案例知识库.txt | 故障案例 | ~15条 | 手工编写，含重复条目，非真实运维记录 |
| 设备成本与产量.txt | 经营数据 | ~100行 | 纯文本格式，未结构化 |

### 1.2 七个根本性问题

**问题1：数据是"快照"不是"过程"**
- 3000行数据覆盖100台设备×30个采样点×7小时
- 真实预测性维护需要数月甚至数年的连续监测数据
- 没有退化轨迹 = 没有RUL预测的基础

**问题2：采样频率太低**
- 每14分钟1次 = 每天~100个数据点
- 工业振动分析需要至少1kHz采样
- 你现在连温度趋势都拟合不准

**问题3：传感器维度太少**
- 只有电流/温度/电压/转速4个维度
- 缺少：振动（最关键）、声发射、油液分析、刀具磨损、主轴位移、冷却液状态
- 4维数据无法支撑真正的故障模式识别

**问题4：故障率不真实**
- 72.3%的故障率远超真实工业场景（通常<5%）
- 故障是"注入"的而非自然退化的，没有演化过程
- 导致所有异常检测算法的基线都是错误的

**问题5：质量数据类型不匹配**
- 质量测试数据是PCB电路板测试（boundary scan, capacitor discharge等）
- CNC机床的质量数据应该是：尺寸精度、表面粗糙度、形位公差
- 两套数据完全脱节，无法建立"设备健康→产品质量"的因果链

**问题6：维护历史缺失**
- 只有"上次维护时间"和"下次维护时间"
- 没有：维护类型、更换了什么备件、停机时长、维修前后状态对比
- 维护历史是RUL建模的标签来源——没有它，退化模型无法训练

**问题7：知识库是"文档"不是"知识"**
- 案例知识库、维护手册都是纯文本
- 没有结构化（故障模式→原因→后果→措施的因果图）
- 没有向量化，无法做语义检索
- 无法被Agent主动调用推理

## 二、企业级数据集架构设计

### 2.1 六层数据架构

企业级预测性维护系统需要6层数据，每层有不同的采集方式、存储方案和消费场景：

| 层级 | 名称 | 内容 | 采集方式 | 存储方案 | 你的现状 |
|------|------|------|----------|----------|----------|
| L1 | 时序传感器数据 | 振动(3轴)/声发射/温度/电流/电压/转速/油压/磨损量/冷却液 | MQTT/Kafka流式 | InfluxDB/TimescaleDB | 有4维，缺振动等关键 |
| L2 | 设备元数据 | 型号/控制器/主轴规格/轴承型号/刀具容量/额定参数 | MES/ERP同步 | PostgreSQL关系表 | 有基本字段 |
| L3 | 维护历史 | 维护类型(PM/CM/CBM)/备件/停机时长/成本/技师笔记 | CMMS/EAM系统 | PostgreSQL+文档 | 仅有维护日期 |
| L4 | 质量数据 | 尺寸精度(CMM)/表面粗糙度/刀具磨损/废品率 | QMS/CMM设备 | PostgreSQL | 有但类型不匹配 |
| L5 | 生产上下文 | 工单/材料/切削参数(进给/切深/转速)/CAM程序/操作员/班次 | MES/SCADA | PostgreSQL | 完全缺失 |
| L6 | 领域知识库 | FMECA/设备手册/维护SOP/故障模式/专家规则/案例 | 人工+文档解析 | 向量DB+规则表 | 有文本，未结构化 |

### 2.2 关键设计原则

**原则1：数据源无关性**
系统设计应与具体数据源解耦。无论数据来自CSV上传、数据库直连还是实时流，Agent都应该能统一消费。这通过定义标准数据接口实现。

**原则2：时序数据分层存储**
- 原始数据（1Hz以上）：InfluxDB，保留3个月
- 降采样数据（每分钟聚合）：PostgreSQL，保留1年
- 特征数据（每小时统计）：PostgreSQL，永久保留
- 这样在保证查询性能的同时控制存储成本

**原则3：维护记录是金标准**
每一次维护操作都是一个"标签事件"——它标记了设备从"某退化状态"回到"健康状态"的转折点。这些标签是训练RUL模型的基础。

## 三、知识库架构设计

### 3.1 当前知识库的问题

你现在的知识库是3个txt文件（案例知识库、设备说明书、维护手册），存在以下问题：

| 问题 | 影响 | 修复方向 |
|------|------|----------|
| 纯文本，未结构化 | Agent无法精确检索特定故障模式的处理方案 | 解析为结构化知识图谱 |
| 无向量化 | 无法做语义相似度检索（"类似CNC_002的电压波动"搜不到） | Embedding + 向量数据库 |
| 案例手工编写 | 案例数量少（~15条），覆盖面窄 | 从历史运维日志自动提取 |
| 无故障传播图 | 无法回答"这个异常如果不处理会导致什么" | 构建FMECA因果链 |
| 无版本管理 | 知识更新后无法追溯 | 知识库带时间戳和来源标记 |

### 3.2 企业级知识库三层架构

**Layer A：结构化规则库（确定性知识）**

存储为关系数据库表，Agent可通过SQL精确查询：

```
故障模式表 (failure_modes)
├── failure_id: 1
├── name: bearing_wear
├── category: mechanical
├── typical_symptoms: ["temp>95", "current_std>2", "speed_jitter"]
├── root_causes: ["lubrication_degradation", "contamination", "fatigue"]
├── failure_effects: ["spindle_runout", "surface_quality_drop", "catastrophic_failure"]
├── criticality: high
├── detection_method: vibration_spectrum_analysis
└── mitigation: replace_bearing + relubricate

故障传播路径表 (failure_propagation)
├── from_failure: power_module_instability
├── to_failure: motor_current_spike
├── probability: 0.78
├── time_lag_hours: 2-6
└── conditions: ["voltage_std>5V"]

维护SOP表 (maintenance_sops)
├── sop_id: SOP-001
├── failure_type: bearing_wear
├── steps: [...]
├── required_parts: [...]
├── estimated_hours: 4.5
├── skill_level: senior_mechanical
└── safety_notes: [...]
```

**Layer B：向量知识库（模糊检索知识）**

将设备手册、维护手册、历史案例、技术报告等非结构化文档向量化存储：

```
文档 → 分块(chunk) → Embedding → ChromaDB/FAISS

检索流程：
  用户问题/Agent推理 → Embedding → 余弦相似度Top-K → 返回相关段落
```

知识库内容应包含：
- 设备技术规格手册（原文）
- 维护SOP完整文档
- 历史故障案例（从运维日志自动提取）
- 行业标准（ISO 10816振动标准、VDI 3832等）
- 专家经验规则（if-then形式）

**Layer C：因果推理图（传播链知识）**

构建故障传播有向图，支持Agent做"如果不处理会怎样"的前向推理和"为什么会这样"的后向溯源：

```
节点 = 故障模式/异常状态
边 = 因果传播关系（含概率和时间滞后）

示例：
  power_module_instability 
    →(p=0.78, lag=2-6h)→ motor_current_spike 
    →(p=0.65, lag=1-3h)→ motor_overheating 
    →(p=0.85, lag=0.5-2h)→ motor_overload 
    →(p=0.92, lag=0.1-0.5h)→ emergency_shutdown

Agent推理示例：
  "CNC_002电压波动" → 前向搜索因果图 → 
  "78%概率2-6小时后电流异常，85%概率后续电机过热"
```

### 3.3 知识库构建路线

| 步骤 | 内容 | 工具 | 产出 |
|------|------|------|------|
| 1 | 解析现有维护手册 | LLM + 正则 | 10种故障的结构化SOP表 |
| 2 | 构建FMECA表格 | 人工+LLM辅助 | 故障模式→原因→后果→检测→缓解 |
| 3 | 构建故障传播图 | 从案例库提取+专家补充 | 有向图（节点~30，边~50） |
| 4 | 文档向量化 | LangChain + ChromaDB | 向量索引，支持语义检索 |
| 5 | 案例自动提取 | 从模拟运维日志中提取 | 100+结构化案例 |
| 6 | 规则引擎 | if-then规则集 | 异常检测→故障诊断规则 |

## 四、数据集生成策略——要不要模拟？

### 4.1 直接回答：要模拟，但不是"造假"，而是"物理仿真"

你的核心困境是：无法获取真实工业数据（属于企业机密），但当前数据集又无法支撑算法验证。

**答案：构建一个基于物理模型的CNC退化仿真器，生成符合工业真实统计特征的合成数据集。**

这不是"伪造数据"——NASA C-MAPSS、PHM Society等权威机构都使用仿真数据做算法基准测试。关键在于仿真必须基于物理原理，使数据具有真实的统计特性。

### 4.2 仿真器设计

**物理模型层（保证数据合理性）：**

| 退化模型 | 物理原理 | 参数 |
|----------|----------|------|
| 轴承退化 | Paris疲劳裂纹扩展模型 | 初始裂纹长度、应力强度因子、材料常数 |
| 电机绕组老化 | Arrhenius热加速模型 | 环境温度、运行温度、激活能 |
| 刀具磨损 | Taylor刀具寿命方程 | 切削速度、进给量、材料硬度 |
| 润滑油劣化 | 指数衰减+污染累积 | 初始粘度、污染源强度 |
| 皮带松弛 | 蠕变模型 | 张紧力、温度、负载循环次数 |

**传感器仿真层（生成多维度时序数据）：**

```
输入：物理退化状态 + 当前工况（切削参数、材料、环境）
  ↓
模型计算：理论传感器读数
  ↓
加噪：工业传感器噪声模型（含1/f闪烁噪声+白噪声+量化噪声）
  ↓
输出：多通道时序数据（15-20维，1Hz采样）
```

**故障注入层（生成标签数据）：**

```
按故障模式（10种）× 严重程度（3级）× 设备役龄（4阶段）组合
  ↓
在退化轨迹的特定时间点注入故障
  ↓
记录：故障开始时间、故障类型、严重程度、演化过程
  ↓
输出：带标签的退化曲线（用于RUL模型训练和验证）
```

## 五、Agent核心功能清单——从L1到L4

### 5.1 L1→L2 需要补齐的能力

| 能力 | 当前 | 目标 | 实现方式 |
|------|------|------|----------|
| 多步推理 | 固定工作流 | 自主选择推理路径 | ReAct模式（Reason+Act循环） |
| 工具调用 | 无 | 能查库/跑算法/画图 | LangGraph工具节点 |
| 案例检索 | 无 | 语义相似案例检索 | 向量DB + Embedding |
| 推理可解释 | 黑盒 | 逐步推理链可视化 | ReAct思考过程透明化 |
| 自我验证 | 无 | 输出结果自检 | Self-Check智能体 + 循环 |

### 5.2 L2→L3 需要补齐的能力

| 能力 | 描述 | 技术方案 |
|------|------|----------|
| 持续监控 | 不是用户问才分析，而是7×24自动巡检 | 定时触发 + 事件驱动 |
| 自适应基线 | 阈值不是写死的，随设备状态自适应更新 | 滑动窗口 + 贝叶斯更新 |
| 增量预测 | 新数据到达时不需要全量重算 | 在线学习 + 增量更新 |
| 主动预警 | 在故障发生前推送预警 | RUL + 风险概率阈值 |
| 多设备并行 | 同时监控50台设备 | asyncio + 并行LangGraph节点 |
| 置信区间 | 不给单点预测值，给区间+概率 | 威布尔 + Bootstrap |

### 5.3 L3→L4 需要补齐的能力

| 能力 | 描述 | 技术方案 |
|------|------|----------|
| 维护排程优化 | 不是"建议维修"，而是"什么时候修、谁修、修多久" | 多目标优化（成本/风险/产能） |
| 成本效益分析 | 维修 vs 不修 vs 延后修的ROI对比 | 蒙特卡洛仿真 + 决策树 |
| What-if仿真 | "如果减载运行能否延长寿命"等假设分析 | 前向仿真 + 参数扫描 |
| 产线级分析 | 考虑设备间依赖和瓶颈传播 | 设备关联图 + 风险传播 |
| 约束处理 | 维护窗口、备件库存、技师可用性 | 约束满足问题(CSP)求解 |
| 人在回路 | 低置信决策升级到人工审批 | 置信度阈值 + 审批工作流 |

### 5.4 企业级Agent的10个核心功能（Checklist）

```
[ ] 1. 多源数据接入    — 支持CSV/MQTT/JDBC/API四种数据入口
[ ] 2. 持续监控引擎    — 定时巡检 + 异常事件触发，非被动响应
[ ] 3. 自适应异常检测  — IQR/Z-score/Isolation Forest + 贝叶斯更新基线
[ ] 4. 根因分析链      — E1-E7证据链 + 因果图后向溯源，每条证据可追溯
[ ] 5. RUL预测+不确定性 — 威布尔退化模型 + P10/P50/P90置信区间
[ ] 6. 案例推理引擎    — 向量检索相似历史案例 + 结构化因果匹配
[ ] 7. 维护决策优化    — 多目标约束优化 + ROI对比 + 排程建议
[ ] 8. 自我验证循环    — 输出结果5项自检，不通过自动重推理（最多3轮）
[ ] 9. 反馈学习机制    — 维护完成后用实际结果更新模型参数
[ ] 10. 推理过程可视化 — ReAct思考链 + 证据链 + 决策树全链路展示
```

## 七、关于"是否模拟数据"的最终建议

### 7.1 明确结论

**是的，你需要模拟一个正常且健全的数据集。** 但不是用random函数"造假"，而是基于物理退化模型构建符合工业统计特征的合成数据集。

### 7.2 为什么必须模拟

| 原因 | 说明 |
|------|------|
| 无法获取真实工业数据 | 企业预测性维护数据属于核心机密，不对外公开 |
| 当前数据无法支撑算法验证 | 7小时30采样点无法训练退化模型 |
| 学术界认可合成数据 | NASA/PHM/CWRU等权威机构都使用仿真数据 |
| 可控性强 | 可以设计特定的退化场景来验证特定算法 |
| 可复现 | 仿真器参数固定后数据可复现，便于对比实验 |

### 7.3 关键约束——仿真必须"物理可信"

你的仿真器必须满足以下约束，否则生成的数据和现在的random数据没有本质区别：

1. **退化曲线必须符合物理模型**：轴承退化用Paris疲劳模型，电机老化用Arrhenius模型，不能是随机游走
2. **传感器噪声必须符合工业特征**：含1/f闪烁噪声+白噪声+量化噪声，不能是纯高斯噪声
3. **故障率必须符合工业统计**：3-5%而非72.3%
4. **故障演化必须有时间过程**：从早期征兆→中期退化→晚期失效的渐进过程，不能突变
5. **维护干预必须有效果**：维护后设备状态应恢复到健康基线附近
6. **多参数必须有物理耦合**：温度升高→电流增大→功率因数变化，不是独立通道
7. **数据量必须足够**：至少覆盖3个月以上的连续监测，每天至少86400个采样点（1Hz）

### 7.4 合规与学术规范

在论文/答辩中使用合成数据时，必须：
- 明确标注数据来源为"基于物理模型的仿真生成"
- 公开仿真器的物理模型和参数设置
- 在公开数据集上做交叉验证，证明算法在不同数据源上都有效
- 不将合成数据伪装为真实工业数据

## 八、总结：你的系统需要完成的三个跨越

```
当前状态                           企业级目标
─────────                          ─────────
数据：7小时快照          ──→       数据：6层×180天×18维
  ↓                                  ↓
知识：3个txt文件         ──→       知识：结构化+向量化+因果图
  ↓                                  ↓
Agent：固定工作流问答    ──→       Agent：ReAct+自验证+决策优化
```

**核心认知转变：**

> 你的系统现在是一个"会说话的报表生成器"——用户问，它查库算数，输出报告。
> 企业级Agent是一个"会思考的维护工程师"——它主动监控、多步推理、量化不确定性、优化决策、自我验证、从反馈中学习。

数据是土壤，知识是根系，算法是树干，Agent是树冠。土壤贫瘠（数据不够）、根系浅薄（知识未结构化），树冠不可能繁茂（Agent能力受限）。

**先修数据，再修知识，最后修Agent——这个顺序不能颠倒。**
