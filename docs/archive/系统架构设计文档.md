# 智维先知 — 企业级Agent系统架构设计

> 本文档定义全新的系统架构：事件驱动诊断流程 + 多Agent协作 + MCP标准化工具 + 模块化Skills + 循环推理 + 分层记忆。

---

## 一、核心设计理念

### 1.1 旧系统的问题

旧系统（Coze平台 4工作流 16节点）本质是**线性管道**：

```
用户提问 → WF1(数据准备) → WF2(RUL计算) → WF3(诊断) → WF4(报告) → 回答
```

问题：被动触发、单次计算、无自检、工具散落、无法学习。

### 1.2 新系统的核心理念

**事件驱动 + 多Agent协作 + 循环推理 + 标准化工具协议**

| 维度 | 旧系统 | 新系统 |
|------|--------|--------|
| 触发方式 | 用户提问 | 数据驱动自动触发 |
| 执行模式 | 线性管道 | 事件驱动 + 循环 |
| 推理深度 | 单次计算 | ReAct多轮推理 |
| 自我验证 | 无 | Reflection循环自检 |
| 工具调用 | Coze节点硬编码 | MCP标准化协议 |
| 知识检索 | 简单文本匹配 | 向量 + 结构化 + 因果图 |
| 记忆能力 | 无 | 四层记忆架构 |
| 输出形式 | 文字回复 | 多模态 + 实时推送 |

## 二、新诊断流程设计

### 2.1 流程总览

6个阶段，事件驱动，包含2个循环回路：

```
Data Stream → Health Monitor → (异常?) 
  ├─ 正常 → 持续监控（循环）
  └─ 异常 → ReAct Diagnostic Loop → Prediction + Decision → Reflection Self-Check
                ↑                                                        ↓
                └──────────── 不通过 · 重推理 ←─────────────────────────┘
                                                                         ↓ 通过
                                                              Output: Alert + Report + Decision
```

### 2.2 六个阶段详解

**阶段1：Data Stream（数据流）**
- 来源：CNC仿真器 → InfluxDB
- 频率：1Hz × 18维传感器
- 触发：持续流入

**阶段2：Health Monitor（健康监控）**
- 运行方式：7×24持续运行
- 算法：四重融合异常检测（Z-score + IQR + CUSUM + 动态基线贝叶斯更新）
- 输出：异常评分(0-100)、异常维度列表、异常类型(突发/渐进/周期性)
- 循环：无异常时持续监控；有异常时触发诊断
- Agent：Monitor Agent
- 调用MCP：mcp-timeseries（查传感器数据）
- 调用Skill：skill-anomaly-detect

**阶段3：ReAct Diagnostic Loop（诊断推理循环）**
- 推理模式：Think → Act → Observe → Think...
- Think："当前异常模式最像哪种故障？需要什么证据？"
- Act：调用MCP工具查知识库、检索案例、遍历故障图
- Observe：收集证据，更新置信度
- 终止条件：confidence > 0.85 或 retry_count >= 3
- 输出：故障类型、根因、E1-E7证据链
- Agent：Diagnostic Agent
- 调用MCP：mcp-knowledge、mcp-analytics
- 调用Skill：skill-evidence-chain、skill-fault-graph

**阶段4：Prediction + Decision（预测 + 决策）**
- RUL预测：威布尔退化模型 + 蒙特卡洛模拟 → P10/P50/P90置信区间
- 贝叶斯更新：用新证据更新退化模型参数
- 决策优化：多目标约束（成本/风险/排程）+ What-if分析
- 输出：RUL预测、维护建议、成本分析、排程方案
- Agent：Prediction Agent + Decision Agent
- 调用MCP：mcp-analytics、mcp-physics（what-if仿真）、mcp-relational（备件/技师）
- 调用Skill：skill-rul-weibull、skill-cost-benefit
- 循环：Decision内部有Planning Loop（分解→执行→监控→重规划）

**阶段5：Reflection Self-Check（反思自检）**
- 5项检查：
  1. 数据完整性：传感器数据是否齐全、时间范围是否覆盖
  2. 逻辑一致性：诊断结论与证据链是否矛盾
  3. 证据链闭合：E1-E7是否每条都有数据支撑
  4. 预测合理性：RUL是否在物理约束范围内
  5. 物理约束校验：退化速率、温度上限等物理约束
- 通过 → 进入Output
- 不通过 → 回到阶段3重新推理（retry_count + 1，最多3次）
- 循环：Reflection Loop（Generate → Critique → Revise）

**阶段6：Output（输出）**
- 告警：飞书/邮件推送（mcp-notify）
- 报告：结构化诊断报告（含证据链、RUL、决策建议）
- 推送：WebSocket SSE实时推送到前端
- 学习：将本次案例存入Episodic Memory（系统越用越聪明）
- Agent：Report Agent
- 调用MCP：mcp-notify
- 调用Skill：skill-report-gen

## 三、多Agent拓扑设计

### 3.1 架构模式：Supervisor + Specialist

采用LangGraph的Supervisor模式：

- **1个Orchestrator（编排者）**：负责路由决策、状态管理、循环控制
- **6个Specialist Agent（专家）**：各自独立，通过State对象传递数据

Orchestrator不直接做业务决策，它只做三件事：
1. 决定下一步调用哪个Agent
2. 管理Agent之间的数据流转（通过State）
3. 控制循环（异常检测回环、自检重试回环）

### 3.2 六个专家Agent

#### Agent 1：Monitor Agent（监控）

| 项 | 内容 |
|----|------|
| 职责 | 持续监控传感器数据，计算异常评分 |
| 触发 | 持续运行（定时器每60秒拉取一次数据） |
| 输入 | equipment_id, time_range |
| 输出 | anomaly_score(0-100), anomaly_dimensions, anomaly_type, baseline_updated |
| 调用MCP | mcp-timeseries（查传感器数据） |
| 调用Skill | skill-anomaly-detect |
| 循环模式 | Memory Loop（每次更新自适应基线） |
| 关键约束 | 基线不能写死，必须随设备状态自适应；18维全检测，不能只看温度电流 |

#### Agent 2：Diagnostic Agent（诊断）

| 项 | 内容 |
|----|------|
| 职责 | 根因分析，构建E1-E7证据链 |
| 触发 | Monitor Agent输出异常评分 > 阈值 |
| 输入 | anomaly_score, anomaly_dimensions, sensor_data |
| 输出 | fault_type, confidence, evidence_chain[E1-E7], root_cause |
| 调用MCP | mcp-knowledge（查FMECA + 向量检索）、mcp-analytics（统计检验） |
| 调用Skill | skill-evidence-chain、skill-fault-graph |
| 循环模式 | **ReAct Loop**（Think → Act → Observe → Think...） |
| 关键约束 | 置信度 > 0.85 才能进入下一阶段；证据链E1-E7每条必须可追溯到具体数据 |

#### Agent 3：Prediction Agent（预测）

| 项 | 内容 |
|----|------|
| 职责 | RUL预测，给出P10/P50/P90置信区间 |
| 触发 | Diagnostic Agent完成 |
| 输入 | fault_type, degradation_history, sensor_data |
| 输出 | rul{p10, p50, p90}, confidence_interval, degradation_curve |
| 调用MCP | mcp-analytics（威布尔拟合）、mcp-timeseries（历史退化数据） |
| 调用Skill | skill-rul-weibull |
| 循环模式 | 无独立循环，但用Memory更新退化模型参数 |
| 关键约束 | 必须给置信区间，不能给单点值；退化速率上限0.005（物理约束） |

#### Agent 4：Decision Agent（决策）

| 项 | 内容 |
|----|------|
| 职责 | 维护决策优化，What-if分析 |
| 触发 | Prediction Agent完成 |
| 输入 | rul, fault_type, equipment_metadata, maintenance_history |
| 输出 | recommendation(immediate/deferred/derated), cost_analysis, schedule, what_if |
| 调用MCP | mcp-physics（what-if仿真）、mcp-relational（查备件/技师排班） |
| 调用Skill | skill-cost-benefit |
| 循环模式 | **Planning Loop**（分解 → 执行 → 监控 → 重规划） |
| 关键约束 | 三选项必须有成本对比；What-if必须包含减载延寿和72小时故障概率 |

#### Agent 5：Knowledge Agent（知识）

| 项 | 内容 |
|----|------|
| 职责 | 知识检索、案例匹配、因果推理 |
| 触发 | 被Diagnostic Agent调用 |
| 输入 | query, symptoms, fault_type |
| 输出 | similar_cases, fault_propagation_paths, sop_recommendations |
| 调用MCP | mcp-knowledge（向量检索 + FMECA查询 + 故障图遍历） |
| 调用Skill | skill-case-match、skill-fault-graph |
| 循环模式 | 无独立循环，作为Diagnostic的支撑工具 |
| 关键约束 | 检索必须语义+结构化双路；因果推理必须支持前向和后向 |

#### Agent 6：Report Agent（报告）

| 项 | 内容 |
|----|------|
| 职责 | 生成自然语言报告，格式化告警，存储案例 |
| 触发 | Reflection Self-Check通过 |
| 输入 | all_state（完整诊断结果） |
| 输出 | report_text, alert_message, summary |
| 调用MCP | mcp-notify（飞书/邮件推送） |
| 调用Skill | skill-report-gen |
| 循环模式 | 无 |
| 关键约束 | 报告必须包含推理过程；每次诊断后自动存入Episodic Memory |

### 3.3 LangGraph作为Harness框架

**Harness = 包裹LLM的外壳**，管理四件事：工具调用、状态流转、循环控制、记忆读写。

LangGraph的核心概念映射：

| LangGraph概念 | 在本系统中的映射 |
|---------------|-----------------|
| StateGraph | 整个诊断流程的有向图 |
| Node | 每个Agent是一个Node |
| Edge | Agent之间的数据流 |
| Conditional Edge | 条件路由（异常? 通过? 重试?） |
| State | 所有Agent共享的状态对象 |
| Checkpointer | 断点续传（长时间推理可恢复） |
| Subgraph | ReAct子图（Diagnostic内部）、Planning子图（Decision内部） |

**State对象设计：**

```python
from typing import TypedDict
import pandas as pd
import numpy as np
from datetime import datetime

class Evidence(TypedDict):
    id: str          # E1-E7
    source: str      # 数据来源
    content: str     # 证据内容
    confidence: float  # 置信度

class AgentState(TypedDict):
    # 输入
    equipment_id: str
    timestamp: datetime

    # Monitor输出
    sensor_data: pd.DataFrame
    anomaly_score: float          # 0-100
    anomaly_dimensions: list[str]
    anomaly_type: str             # sudden/gradual/periodic

    # Diagnostic输出
    fault_type: str
    confidence: float             # 0-1
    evidence_chain: list[Evidence]  # E1-E7
    root_cause: str

    # Prediction输出
    rul: dict[str, float]        # {"p10": 120, "p50": 240, "p90": 480}
    degradation_curve: np.ndarray

    # Decision输出
    recommendation: str           # immediate_repair/deferred/derated
    cost_analysis: dict
    schedule: dict
    what_if: dict

    # Reflection输出
    self_check_result: dict[str, bool]

    # 元数据
    retry_count: int
    max_retries: int              # 3
    reasoning_trace: list[str]    # 推理过程记录（可解释性）
```

## 四、MCP服务器设计

### 4.1 为什么要用MCP

MCP (Model Context Protocol) 是标准化的工具调用协议。

| 旧方式（Coze节点） | MCP方式 |
|-------------------|---------|
| 每个Agent直接写数据库查询 | 通过MCP标准接口调用 |
| 工具散落在各Agent代码中 | 工具集中管理在MCP Server |
| 新增工具需要改Agent代码 | 新增MCP Server即可，Agent无需改动 |
| 无法跨Agent复用工具 | 所有Agent共享MCP工具池 |
| 没有权限控制 | MCP可以定义权限和速率限制 |
| 调试困难（工具逻辑混在业务代码里） | 工具独立进程，可单独测试 |

## 五、Skills设计

### 5.1 Skill vs MCP的区别

| 维度 | MCP Server | Skill |
|------|-----------|-------|
| 角色 | 工具提供者（底层操作） | 能力封装（业务流程） |
| 粒度 | 细粒度（单个操作，如查一条数据） | 粗粒度（完整流程，如构建证据链） |
| 复用 | 跨Agent共享（所有Agent都能用） | 通常单个Agent专用 |
| 状态 | 无状态 | 可有状态（如自适应基线） |
| 实现 | 独立进程 | Python模块/函数 |
| 类比 | 数据库客户端 | 业务逻辑层 |

关系：**Agent → 调用Skill → Skill内部调用MCP工具**

```
Diagnostic Agent
  → 调用 skill-evidence-chain
    → skill内部调用 mcp-knowledge.query_fmeca()
    → skill内部调用 mcp-knowledge.traverse_fault_graph()
    → skill内部调用 mcp-analytics.cusum_detect()
    → 整合结果，输出E1-E7证据链
```

### 5.2 七个Skills

#### Skill 1：skill-anomaly-detect

```python
async def detect(
    sensor_data: pd.DataFrame,
    baseline: Baseline
) -> AnomalyResult:
    """
    四重融合异常检测

    算法：
    1. Z-score检测：各维度Z-score超过3σ标记异常
    2. IQR检测：超出[Q1-1.5*IQR, Q3+1.5*IQR]标记异常
    3. CUSUM累积和：检测参数累积偏移趋势
    4. 动态基线：滑动窗口(7天)自适应基线 + 贝叶斯更新

    融合策略：四种方法各输出0-100评分，加权融合(各0.25)
    若两种以上同时报警，评分额外加权

    Returns:
        AnomalyResult(score=0-100, dimensions=[...], type="gradual")
    """
```

#### Skill 3：skill-rul-weibull

```python
async def predict_rul(
    degradation_data: pd.DataFrame,
    fault_type: str
) -> RULResult:
    """
    威布尔退化模型RUL预测

    流程：
    1. 从退化数据提取退化轨迹

        RULResult(p10=120, p50=240, p90=480, curve=np.ndarray)
    """
```

## 六、循环模式设计

### 6.1 四种循环模式

#### 循环1：ReAct Loop（诊断推理）

| 项 | 内容 |
|----|------|
| 位置 | Diagnostic Agent内部 |
| 触发 | 异常检测命中 |
| 流程 | Think("什么故障？") → Act(查知识库) → Observe(看到证据) → Think("够不够？") → ... |
| 终止 | confidence > 0.85 或 retry_count >= 3 |
| LangGraph实现 | 子图，条件边回环 |

```python
# LangGraph实现
react_subgraph = StateGraph(ReActState)
react_subgraph.add_node("think", think_node)
react_subgraph.add_node("act", act_node)
react_subgraph.add_node("observe", observe_node)

react_subgraph.set_entry_point("think")
react_subgraph.add_edge("think", "act")
react_subgraph.add_edge("act", "observe")
react_subgraph.add_conditional_edges("observe", should_continue, {
    True: "think",    # 继续推理
    False: "done"     # 进入下一阶段
})
```

#### 循环2：Reflection Loop（自我验证）

| 项 | 内容 |
|----|------|
| 位置 | Prediction + Decision之后 |
| 触发 | 每次输出前 |
| 流程 | Generate → Critique(5项检查) → Revise(如果不通过) |
| 终止 | 5项全通过 或 retry_count >= 3 |
| 5项检查 | 数据完整性、逻辑一致性、证据链闭合、预测合理性、物理约束 |

```python
def reflection_node(state: AgentState) -> AgentState:
    checks = {
        "data_complete": check_data_completeness(state),
        "logic_consistent": check_logic_consistency(state),
        "evidence_closed": check_evidence_chain(state),
        "prediction_reasonable": check_prediction(state),
        "physics_valid": check_physics_constraints(state)
    }
    all_pass = all(checks.values())
    if all_pass or state["retry_count"] >= state["max_retries"]:
        return {"next": "output"}
    else:
        return {"next": "diagnose", "retry_count": state["retry_count"] + 1}
```

#### 循环3：Planning Loop（决策规划）

| 项 | 内容 |
|----|------|
| 位置 | Decision Agent内部 |
| 触发 | RUL预测完成 |
| 流程 | Decompose(分解子问题) → Execute(逐个求解) → Monitor(评估效果) → Replan(如果需要) |
| 终止 | 找到最优方案 |

#### 循环4：Memory Loop（学习循环）

| 项 | 内容 |
|----|------|
| 位置 | 全局，贯穿所有Agent |
| 流程 | Store(存储经验) → Retrieve(检索相关) → Update(更新模式) |
| 终止 | 持续运行 |
| 关键 | 每次成功诊断后自动存入Episodic Memory，系统越用越聪明 |

### 6.2 在LangGraph中的完整图结构

```python
from langgraph.graph import StateGraph, END
from langgraph.checkpoint import MemorySaver

graph = StateGraph(AgentState)

# 主节点
graph.add_node("monitor", monitor_node)
graph.add_node("diagnose", diagnose_node)    # 内部含ReAct子图
graph.add_node("predict", predict_node)
graph.add_node("decide", decide_node)        # 内部含Planning子图
graph.add_node("reflect", reflection_node)
graph.add_node("output", output_node)

# 主边
graph.set_entry_point("monitor")

# 条件边：Monitor → 异常?
graph.add_conditional_edges("monitor", check_anomaly, {
    True: "diagnose",    # 有异常，进入诊断
    False: "monitor"    # 无异常，继续监控
})

# 线性边
graph.add_edge("diagnose", "predict")
graph.add_edge("predict", "decide")
graph.add_edge("decide", "reflect")

# 条件边：Reflection → 通过?
graph.add_conditional_edges("reflect", check_self, {
    True: "output",     # 通过，输出结果
    False: "diagnose"   # 不通过，重新诊断
})

graph.add_edge("output", END)

# 编译（带断点续传）
app = graph.compile(checkpointer=MemorySaver())
```

## 七、记忆架构

### 7.1 四种记忆

| 类型 | 存储位置 | 内容 | 生命周期 | 检索方式 |
|------|----------|------|----------|----------|
| Working Memory | LangGraph State | 当前分析会话的状态 | 单次会话 | 直接访问State对象 |
| Episodic Memory | ChromaDB + PostgreSQL | 历史故障案例（设备ID、故障类型、参数序列、根因、维修总结） | 永久 | 向量检索 + 结构化查询 |
| Semantic Memory | FMECA表 + 向量库 | 领域知识（故障模式、症状、根因、后果、检测方法、SOP） | 永久 | SQL查询 + 向量检索 |
| Procedural Memory | SOP表 | 维护流程（步骤、所需工具、预估工时、安全注意事项） | 永久 | SQL查询 |

### 7.2 记忆读写时机

```
Monitor Agent
  → 写入 Working Memory（传感器数据、异常评分、更新后的基线）

Diagnostic Agent
  → 读 Episodic Memory（检索相似历史案例）
  → 读 Semantic Memory（查询FMECA故障模式）
  → 写 Working Memory（证据链、根因、置信度）

Prediction Agent
  → 读 Working Memory（退化数据、故障类型）
  → 写 Working Memory（RUL预测、退化曲线）

Decision Agent
  → 读 Procedural Memory（查询维护SOP）
  → 写 Working Memory（决策建议、成本分析）

Report Agent
  → 读 Working Memory（读取全部状态）
  → 写 Episodic Memory（将本次案例存入，供未来检索）
```

**关键设计：每次成功诊断后，Report Agent自动将本次案例存入Episodic Memory。下次遇到类似问题时，Diagnostic Agent可以直接检索到。系统越用越聪明。**

- Skill必须有Google风格docstring
- Skill文件不超过200行

- Agent之间通过State传递数据，不使用全局变量
- 每个Agent输出必须包含reasoning（推理过程字符串）
- 条件边函数必须有明确的True/False返回
