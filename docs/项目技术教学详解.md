## 第 0 章 开场白：这个项目到底是什么

一句话：**智维先知是一个"预测性维护"智能体系统**。100 台 CNC 数控机床 24 小时上报
22 维传感器遥测（温度、电流、振动、主轴转速……），系统不是等人来问，而是**自己**：
发现异常 → 自动诊断故障 → 查知识库对证 → 预测还能撑多久(RUL) → 决定怎么处理 →
写报告 → 自己检查报告写得对不对。管理员只在"高风险的处置报告"上点一下"批准"。

在这条链背后，是 **LangGraph 把 8 个专业 agent 编排成一张有向图**，让它们像流水线一样
接力，还能"返工"。你要学的，就是这张图是怎么画出来、怎么跑起来的。

为了讲清楚，我会反复用**三个层次**组织讲解：

| 层 | 问题 | 在本项目里的形态 |
|---|---|---|
| **概念层** | 这个技术"是什么、解决什么" | ReAct、RRF、checkpoint… |
| **代码层** | 在这个项目里"怎么写" | 精确到文件 + 行号 + 摘录 |
| **工程层** | "为什么这么取舍、怎么调优" | 降级链、确定性、可追溯 |

先记住四个贯穿全文的**工程执念**，后面到处都是它们的影子：

1. **确定性优先**：纯算法的 skill 不调大模型，同样输入必得同样输出——好审计、好演示、好测试。
2. **可追溯**：每次 skill 调用、每次 LLM 调用、每批数据都留痕（trace_id / tool_calls.jsonl / data_provenance）。
3. **优雅降级**：DeepSeek 没 key → 本地 Ollama；Ollama 挂 → 模板兜底。**演示永远不白屏。**
4. **诚实**：报告数据全部来自真实库或真实检索，绝不编造。

## 第 2 章 从零学 LangGraph：怎么"画"一个智能体

这一章是整个讲义的地基。我们不直接背概念，而是**跟着项目图 A 走一遍**，你自然会懂
LangGraph 的核心 API。

### 2.1 一个智能体 = 一张图，图 = 节点 + 边

LangGraph 的世界观很简单：

- **State（状态）**：一张"共享黑板"，所有节点都在上面读、写。节点之间不直接传参，
  都通过这块黑板交流。
- **Node（节点）**：一个函数，输入整块黑板，返回要改写的部分。
- **Edge（边）**：决定流程走向。分普通边(顺序执行)和**条件边**(函数返回字符串选下一节点)。
- **Graph → compile()**：把图画成可执行对象，之后 `invoke` / `ainvoke` 跑起来。
- **Checkpointer**：把每一轮跑的状态存起来，支持"断点续跑、多轮会话记忆"。

> **老师点评**：LangGraph 之所以比裸调 LLM 强，在于它把"状态管理"和"流程控制/循环"
> 从你手写的 `while` + 大字典里**解放出来**，让多 agent 协作的图可视、可暂停、可恢复、
> 可人类介入。你要习惯"用图思考"而不是"用 if-else 思考"。

### 2.2 跟着图 A 认 API（`src/graph/main_graph.py`）

```python
workflow = StateGraph(DiagnosticState)          # ① 定义一张"黑板"长什么样
workflow.add_node("monitor",    monitor)        # ② 加 7 个节点（都是函数）
workflow.add_node("diagnostic", diagnostic)
workflow.add_node("knowledge",  knowledge)
workflow.add_node("prediction", prediction)
workflow.add_node("decision",   decision)
workflow.add_node("report",     report_node)
workflow.add_node("reflection", reflection_node)
workflow.add_edge(START, "monitor")              # ③ 起点 → 第一节点
workflow.add_conditional_edges("monitor", route_monitor,
    {"diagnostic": "diagnostic", "end": END})    # ④ 条件边：看要不要继续诊断
workflow.add_edge("diagnostic", "knowledge")     # ⑤ 顺序边
# …（省略中间顺序边）…
workflow.add_conditional_edges("reflection", route_reflection,
    {"retry": "diagnostic", "end": END})         # ⑥ 反射→可回退重跑
return workflow.compile(checkpointer=MemorySaver())  # ⑦ 编译 + 挂 checkpoint
```

对照概念：`StateGraph(DiagnosticState)` 是"黑板类型"，7 个 `add_node` 是流水线工位，
`add_edge` 是传送带，`add_conditional_edges` 是一个"分流闸"(函数返回字符串决定去向)，
`compile(checkpointer=MemorySaver())` 出厂。

### 2.3 State：黑板到底写了什么（`src/agents/state.py`）

```python
class DiagnosticState(TypedDict, total=False):
    machine_id: str
    readings: Annotated[list, operator.add]          # 追加合并，不覆盖
    ...
    events: Annotated[list, operator.add]
    messages: Annotated[list[BaseMessage], add_messages]  # 消息累积
    health_score: float
    fault_code: int | None
    ...
    reflection_passed: bool
    retry_count: int
```

这里藏着 LangGraph 最精妙的一招——**Reducer（归约器）**。`Annotated[list, operator.add]`
的意思是：任何节点返回一个 list 时，不是覆盖黑板里已有的 list，而是**拼接进去**。
`Annotated[list[BaseMessage], add_messages]` 同理，专门用来累积多轮对话消息。

> **老师点评**：如果不用 reducer，每个节点都得自己把黑板里的历史 list 读出来再拼回去，
> 极易写错。LangGraph 帮你声明式地解决"合并规则"，你只管返回"我这一节点新增了什么"。

### 2.4 条件边 = LangGraph 里的"循环与分支"

图 A 有两条条件边，你必须看懂：

```python
# 分流闸 1：monitor 之后要不要真诊断？
def route_monitor(state):
    if state.get("is_anomaly") and not state.get("error"):
        return "diagnostic"     # 有异常 → 进诊断
    return "end"                # 无异常 → 直接结束

# 分流闸 2：reflection 自我检查不通过 → 回到 diagnostic 重来
def route_reflection(state):
    if state.get("reflection_passed") or state.get("retry_count", 0) >= 3:
        return "end"            # 检查通过 / 已重试 3 次 → 结束
    return "retry"              # 否则回 diagnostic 重做（retry_count+1）
```

**这就是"图里的循环"**：`"retry" → diagnostic` 会让控制流绕回去重跑，直到通过或到达
重试上限。它像一个 `for` 循环，LangGraph 帮你计数(在 state 里手动维护 `retry_count`)。

> **易错点（老师考你）**：很多人以为"反思= ReAct"。**不是**。在 LangGraph 里，最外层
> 的反思重试是一个**固定图 + 条件边 + 计数器**的循环；而 ReAct 是"让 LLM 自己决定
> 下一步调哪个工具"的另一种循环，通常**藏在单个节点内部**。本项目的 ReAct 在
> `analysis` 节点里（第 6 章细讲），外面的图是固定流水线。**别把两层混为一谈。**

### 2.5 图上手实践清单（你自己做一遍）

想真正会画图，动手写一个最小图：

```python
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, END
import operator

class S(TypedDict):
    n: int
    log: Annotated[list[str], operator.add]

def inc(s: S):  return {"n": s["n"] + 1, "log": [f"inc->{s['n']+1}"]}
def gate(s: S): return "again" if s["n"] < 3 else "done"

g = StateGraph(S)
g.add_node("inc", inc)
g.set_entry_point("inc")
g.add_conditional_edges("inc", gate, {"again": "inc", "done": END})
r = g.compile().invoke({"n": 0, "log": []})
print(r)  # {'n': 3, 'log': ['inc->1','inc->2','inc->3']}
```

看懂这个，你对 LangGraph 的节点/条件边/循环就有了肌肉记忆。

## 第 3 章 模型怎么调用、怎么路由、怎么调优

### 3.1 一套代码，两个 Provider（本地 Ollama + 云端 DeepSeek）

`src/llm/client.py` 的 `UnifiedLLMClient` 用 **httpx 直接发 HTTP**，不依赖 openai SDK：

```python
# 本地 Ollama（qwen2.5:7b，跑在自己电脑上）
POST {OLLAMA_BASE_URL}/api/chat            # 对话
POST {OLLAMA_BASE_URL}/api/embed           # 文本向量（bge-m3）
# 云端 DeepSeek（deepseek-chat）
POST {DEEPSEEK_BASE_URL}/chat/completions  # 兼容 OpenAI 格式
```

为什么能"一套代码两家通吃"？因为 DeepSeek 提供了 **OpenAI 兼容接口**（同样的
`/chat/completions` + JSON 结构），Ollama 的 `api/chat` 也尽量贴近。所以客户端只需按
provider 拼不同 URL，请求体结构几乎一样。这就是"模型无关（provider-agnostic）"。

**凭据安全**：key 只从 `.env` 读（`os.getenv("DEEPSEEK_API_KEY")`），绝不硬编码。客户端有
`deepseek_enabled` 属性，没配 key 就自动切本地。

### 3.2 路由表：让"对的人用对的模型"（`src/config/model_routing.py`）

不是所有节点都用同一个模型——那样又贵又慢。用一张**路由表**按 agent 分工分配：

| agent 节点 | provider | 模型 | 温度 | 为什么 |
|---|---|---|---|---|
| monitor(监控) | ollama | qwen2.5:7b | 0.1 | 判断"有没有异常"，要快、要稳，温度低少发散 |
| diagnostic(诊断) | deepseek | deepseek-chat | 0.3 | 重推理，值得花钱 |
| prediction(预测) | deepseek | deepseek-chat | — | 要给 RUL 区间，推理重 |
| decision(决策) | deepseek | deepseek-chat | — | 给分级处置建议 |
| knowledge(知识) | ollama | qwen2.5:7b | — | 查库对证，轻量 |
| report(报告) | deepseek | deepseek-chat | — | 长文组织 |
| reflection(反思) | ollama | qwen2.5:7b | 0.0 | 只做"通过/不通过"判断，温度 0 最可靠 |
| chat(聊天) | ollama | qwen2.5:7b | 0.3 | 问答，轻量本地即可 |

每个 agent 的配置是 `AgentModelConfig`：provider / model / temperature / max_tokens /
context_window / system_prompt 等。**这就是"模型调优"的第一个旋钮——不是只调模型权重，
而是选对模型、配对温度、给对系统提示。**

### 3.3 温度与上下文窗口：两个最常调的旋钮

- **temperature（温度）**：越低越确定/保守，越高越发散/有创意。
  - 分类、校验、判断类任务(monitor/reflection) → 低温度，甚至 `0.0`，要它"别发挥"。
  - 生成报告、组织回答(chat/report) → 稍高一点点，但要守住事实，不宜过高。
- **context_window / max_tokens**：上下文窗口是模型一次能"看到"的 token 上限；
  `max_tokens` 是单次回复最多输出多少。诊断要读很多上下文 → 窗口给到 32k；
  监控只扫一段 → 4k 就够，省钱省延迟。

> **老师点评**：给学生的"调优三板斧"：①按任务选模型和温度；②控制上下文体积(只喂相关
> 片段，见第 8 章上下文工程)；③设好降级路径防止演示翻车。

### 3.4 降级链（这个项目最值得抄的工程经验）

真实场景里云端随时可能没 key / 限流 / 断网。项目做了**多层降级**，每一层都保证"还能出
活"：

```
DeepSeek 无 key/超时
   └→ 切本地 Ollama qwen2.5:7b
诊断的 LLM 增强不可用（ENABLE_LLM_ENRICHMENT=0 默认关）
   └→ 走确定性规则 _select_fault_code()，不依赖 LLM
聊天 compose 时 LLM 异常
   └→ _template_answer() 用模板把工具结果拼成答案（不润色但有内容）
检索层 Ollama(bge-m3) 挂
   └→ 纯 BM25 词法通道照常召回
```

**记住**：智能体系统的第一原则不是"要强"，而是"要稳"。评委最怕你现场黑屏，降级链就是
你的安全网。

## 第 4 章 Skill 系统：把"能力"工程化（包 + 注册表 + 契约）

### 4.1 为什么要"包目录化"而不是"单个 .py"

改造前 `src/skills/` 下既有**包**又有**平铺函数文件**，风格混乱，导致：
- 能力无法被统一**发现/列举**（聊天 agent 和前端都不知道"系统会哪些招"）；
- 无法统一**记录**谁调了什么、耗时多少、是否确定性；
- 调用路径五花八门，新 skill 接入靠手改。

改造后定下铁律：**每个 skill 必须是一个包，固定 4 个文件**：

```
src/skills/<skill_id>/
├── __init__.py    # 只导出一个实例：SKILL = XxxSkill()
├── skill.py       # class XxxSkill(BaseSkill)，实现 run()
├── schema.py      # pydantic 输入/输出模型（对外契约）
└── SKILL.md       # 人读文档（用途/入参/出参/示例/是否确定性/副作用）
```

### 4.2 三件套契约 = 让"能力"可被机器读懂（`src/skills/base.py`）

每个 skill 继承 `BaseSkill`，用类变量声明三件套。这三件套让系统**不用执行 skill 逻辑**
就能拿到它的元数据、生成 LangChain 工具、校验入参出参：

```python
class BaseSkill:
    meta: ClassVar[SkillMeta]             # 身份证：id/名称/分类/是否确定性/标签/示例
    input_schema: ClassVar[type[BaseModel]]   # 输入长什么样（pydantic 契约）
    output_schema: ClassVar[type[BaseModel]]  # 输出长什么样
    def run(self, payload): ...           # 子类实现真实算法
    def to_langchain_tool(self) -> StructuredTool: ...  # 暴露给 ReAct 型 agent
```

> **老师点评**：`input_schema`/`output_schema` 是 pydantic 模型，等于给每个 skill 定义了
> **接口文档 + 运行时校验**。任何人(API、前端、LLM)都知道"调用这个 skill 该传什么、会
> 拿回什么"。这就是面向契约编程(contract-first)。

### 4.3 注册表：自动发现 + 统一执行 + 审计

`SkillRegistry`（也在 `base.py`）是一个类级字典 `_skills`。核心三招：

```python
# ① 自动发现：扫 src/skills/ 下的子包，凡导出了 SKILL 实例就登记
@classmethod
def discover(cls):
    for module in pkgutil.iter_modules([str(root)]):
        if not module.ispkg: continue
        package = importlib.import_module(f"src.skills.{module.name}")
        skill = getattr(package, "SKILL", None)      # 找 SKILL 实例
        if isinstance(skill, BaseSkill):
            cls._skills[skill.meta.id] = skill       # 登记
    return cls.all()

# ② 唯一执行入口：校验入参 + 执行 + 写审计日志
@classmethod
def run(cls, skill_id, payload, *, caller="api"):
    skill = cls.get(skill_id)
    started = time.perf_counter()
    result = skill.run(skill.input_schema(**payload))   # 用 pydantic 校验 payload
    tool_call(caller=caller, tool=skill_id, args=payload, latency_ms=..., ...)  # 审计
    return result.model_dump()
```

要点：
- `discover()` 是**幂等**的，可在启动 lifespan 里反复调；单个 skill import 失败只跳过
  并记日志，**不会拖垮整个启动**——这是"宁可少一个能力，不可全挂"的健壮性设计。
- `run()` 是**唯一会写 `tool_calls.jsonl` 的入口**，于是"agent 到底调了什么"永远可查。
- 用 pydantic `input_schema(**payload)` 在入口统一校验，非法入参直接抛错，不污染核心逻辑。

### 4.4 三层调用方式（按场景选，别混用）

| 方式 | 代码 | 何时用 |
|---|---|---|
| ① 注册表统一入口 | `SkillRegistry.run("rul_weibull", {...})` | API / 审批链，需要审计 |
| ② 直接 execute | `SkillRegistry.get("rul_weibull").execute(**kw)` | 内部代码，仍走校验 |
| ③ LangChain Tool | `skill.to_langchain_tool()` | 给 ReAct 型 agent 当工具 |

### 4.5 例子：rul_weibull（威布尔 RUL）skill

看 `src/skills/rul_weibull/schema.py` 与 `skill.py`：

```python
class RULInput(BaseModel):          # 入参契约
    history: list[dict[str, float]]
    health_score: float = Field(default=0.8, ge=0.0, le=1.0)
    anomaly_score: float = Field(default=0.2, ge=0.0, le=1.0)

class RULOutput(BaseModel):         # 出参契约
    rul_p10: int; rul_p50: int; rul_p90: int
    degradation_rate: float; monitoring_freq: str
    beta: float; eta: float; confidence: float
    @property
    def ordered(self) -> bool: return self.rul_p10 > self.rul_p50 > self.rul_p90
```

注意 `predict_rul()` 是**纯函数**：输入历史温升/电流趋势 → 拟合 Weibull → 输出区间。
它遵守一条**领域约定**：本项目里 P10 是"乐观长寿命界"，所以强制 `P10 > P50 > P90`
（`ordered` 属性就是自我校验）。这就是"确定性 skill"——不调 LLM，同样输入必得同样输出。

## 第 5 章 RAG：知识库召回全拆解

### 5.1 为什么需要 RAG

LLM 的知识是"训练时"的，不知道你这套设备的维护手册、历史案例、成本数据。RAG
(Retrieval-Augmented Generation) = **先检索相关知识片段，再把这些片段塞进 prompt 让
LLM 作答**。本项目还用 RAG 直接喂给诊断/聊天做"对证"，减少幻觉。

### 5.2 全链路（跟着数据流走一遍）

```
data/knowledge/*.txt（4 个源：维护手册/设备说明书/案例库/成本产量）
   │
   ▼ src/knowledge/chunking.py      结构感知切分
   │     把长文切成"检索单元"，且把标题路径写进每块正文
   ▼ src/knowledge/index_builder.py  build()
   │     ├─ BM25 稀疏索引 → data/index/bm25.pkl
   │     ├─ bge-m3 稠密索引 → data/chroma_db（1024 维）
   │     └─ fingerprint.json（sha256，判断要不要重嵌）
   ▼ 查询时 src/knowledge/retrieval.py  HybridRetriever.search(query)
         稠密 top_k  +  稀疏 top_k  →  RRF 融合  →  元数据过滤  →  top_n
```

### 5.3 切分：结构优先，不是硬切 N 字

不同文档结构差异大，不能一刀切。chunking 的**两级策略**：
1. **按标题切**：识别 markdown `#`、`### 故障类型N`、`一、二、三`、`【案例NNN】` 等边界，
   把不同主题拆开（避免把"轴承故障"和"电机故障"塞进同一块）。
2. **超长兜底**：单块超过 `max_chars=480` 才按句滑窗切，`overlap_chars=80` 让上下文不
   在边界硬断。过短的碎片(`<min_chars=24`)并回前一块。

最妙的一招——**把标题路径写进正文**：

```
原文块可能只是：「3. 拆卸主轴箱侧盖，检查轴承游隙与润滑脂状态」
写进向量的正文是：「【维护手册 > 故障类型1：轴承磨损 > 标准维修步骤】
                       3. 拆卸主轴箱侧盖，检查轴承游隙与润滑脂状态」
```

为什么有效？因为向量化和 BM25 都只看文本。如果正文是孤立的"拆卸主轴箱侧盖"，它和
"轴承磨损怎么修"的语义距离很远；加上标题路径后，词法命中"轴承磨损/维修/主轴"，
向量也能看到上下文。**这是提升召回率性价比最高的一招**。

### 5.4 双通道 + RRF 融合（`retrieval.py`）

两个检索通道各有所长，融合：

- **稠密（Dense）**：bge-m3 把查询和文档都变成向量，算余弦相似度。**能懂语义**——用户
  问"发热"，它能匹配写"温升"的文档。
- **稀疏（Sparse/BM25）**：经典词法检索，算关键词命中的 TF-IDF。**能抓精确实体**——问
  "CNC_023"、"故障码7"，词法一打一个准；且不依赖嵌入模型、Ollama 挂了还能用。

融合算法选 **RRF（Reciprocal Rank Fusion）** 而不是"分数加权"，原因见代码头注释：
**BM25 分数无界、向量相似度 ∈[-1,1]，量纲不可比**，直接加权会偏袒大数值那一路。
RRF 只取排名：`score = Σ w/(RRF_K + rank)`，每个通道贡献的是"排名分"而非"原始分"，
更公平、对单通道失效更鲁棒。

```python
def reciprocal_rank_fusion(rankings, *, k=60, weights=None):
    fused = {}
    for ch_i, ranking in enumerate(rankings):
        w = weights[ch_i] if weights and ch_i < len(weights) else 1.0
        for rank, (identifier, _) in enumerate(ranking, start=1):
            fused[identifier] = fused.get(identifier, 0.0) + w / (k + rank)
    return sorted(fused.items(), key=lambda x: x[1], reverse=True)
```

权重：`bm25_weight=1.0, dense_weight=0.9, RRF_K=60`。同分时优先"BM25 命中术语多的文档"。

### 5.5 召回率怎么评估、怎么调（`scripts/rag_tools.py`）

评估脚本内置 12 条"带预期命中词的查询"（如「CNC_023 上次维修时间」应命中某案例），算
**recall@k**：

```bash
.venv/Scripts/python.exe scripts/rag_tools.py build   # 重建索引
.venv/Scripts/python.exe scripts/rag_tools.py eval    # recall@5
```

**实测结果：recall@5 = 1.0（12/12 全命中），其中 11 条 top1 就命中。** 这个数字是你
答辩时最有说服力的"数据驱动"证据。

**调优手段(按性价比排序)**：
1. 标题路径前置正文（做了）；
2. 同义词双向扩展（`chunking.py` SYNONYM_GROUPS，如"发热/温度/高温"一组），只扩 BM25
   侧不稀释稠密语义（做了）；
3. 元数据过滤（`fault_code`/`machine_id`），诊断时精准召回；
4. 指纹增量重建，源文件没变就不重嵌，启动秒级；
5. 若 recall 不够 → 加测试查询、调 RRF_K / 权重 / 切分块大小，跑 eval 迭代。

> **老师点评**：RAG 调优要"有标尺"。先有一套固定测试查询(黄金集)，每次改动跑一次
> recall，用数字说话，而不是凭感觉改参数。

## 第 6 章 Tool 与 ReAct：让 LLM"会用工具"

### 6.1 两种"工具"要分清（老师反复强调的坑）

项目里其实有**两套**能力供给，千万别混：

| 体系 | 在哪 | 本质 | 当前怎么被用 |
|---|---|---|---|
| **Skills 体系** | `src/skills/*` + `SkillRegistry` | 确定性算法，契约化、注册表化 | 函数级 import + `SkillRegistry.run()` |
| **本地 @tool（ReAct）** | `src/agents/analysis.py` | 喂给 ReAct agent 的 LangChain 工具 | 在 `analysis` 节点内部 |

`analysis.py` 里这样声明工具（`@tool` 装饰器把函数变 LangChain Tool）：

```python
@tool
def analyze_temperature(history: list[float], ...) -> dict:
    """三信号融合做温升异常检测……"""   # docstring 就是给 LLM 看的使用说明
    ...

@tool
def estimate_rul(...) -> dict: ...
```

`create_react_agent(model=llm, tools=TOOLS)` 让 LLM 在一个节点内自主决定调哪个工具。

### 6.2 ReAct = Reasoning + Acting（想一步，做一步，看结果再想）

ReAct 的核心循环是给 LLM 的每一步都包含**三条消息**：

```
Thought:  我现在该干什么？（推理）
Action:   调哪个工具、传什么参数？（行动）
Observation: 工具返回了什么结果？（观察）
Thought:  ……（根据观察继续推理，直到不需要工具，输出最终答案）
```

LangChain 的 `create_react_agent` 帮你封装了这套 prompt + 解析 + 循环。你只要：
1. 定义好一批 `@tool`；
2. 告诉它"你有哪些工具、每个工具干嘛"（工具 docstring 就是给 LLM 的说明书）；
3. 它自己会决定"用不用、用哪个、用完怎么继续"。

> **老师点评**：ReAct 适合"没有固定流程、靠推理动态选工具"的任务。而本项目**主流程是
> 固定流水线**(监控→诊断→…→反思)，所以 ReAct 只用在需要"灵活分析"的 `analysis` 节点，
> 外层用固定图。**选型原则**：能定死流程就别用 ReAct(贵、慢、不可控)；需要动态决策才上
> ReAct。这也回答了很多人的困惑——"为什么这系统不是全 ReAct？"

### 6.3 关键追问：Skills 到底有没有接进 ReAct？

**诚实回答：没有。** `SkillRegistry.as_langchain_tools()` 这个批量转换方法被定义了，
但当前**没有任何 ReAct agent 调用它**。Skills 现在通过两条真实路径被用：
1. **函数级**：`diagnostic_agent.py` 直接 `from src.skills.case_match import match_cases`
   调函数（图节点内部，性能好、可测）；
2. **注册表级**：审批链 `SkillRegistry.run("maintenance_report", ...)` 和 `/api/skills/{id}/run`。

**这正是你可以给评委讲的"未来演进点"**：要把 skills 接进 ReAct，只需在某节点改用
`create_react_agent(model, tools=SkillRegistry.as_langchain_tools(...))`，让 LLM 动态挑
skill。三层设计(`to_langchain_tool`)已经为这条将来之路铺好了路。

## 第 7 章 Loop：项目里的"循环"到底长什么样

"循环"在本项目有**三种**完全不同的形态，搞清楚它们你就掌握了智能体编排的精华：

### 7.1 图内条件边循环（LangGraph 原生）

图 A 的 `reflection → retry → diagnostic`、图 B 的 `self_check → fail → analysis`。
这是**"自我反思 + 返工"**的经典实现：跑完一轮，用一个节点自我检查质量，不合格就绕回
关键节点重做，最多 N 次。靠 state 里的计数器(`retry_count`)控制上限，防死循环。

### 7.2 ReAct 内循环（藏在节点里）

`analysis` 节点里 `create_react_agent` 让 LLM Thought→Action→Observation 自行迭代，
直到它能给出结论。这是"由 LLM 决定何时停"的循环。

### 7.3 自主外循环（`src/agents/autonomous_loop.py`，不是图！）

前两种都是"一次请求内的循环"，而**自主循环是跨请求、长期运行的守护进程**：

```python
async def _run(self):
    while not self.stop_event.is_set():      # 30 秒一个节拍
        for machine_id in self._machines:     # 扫每台设备
            await self._run_diagnostic(machine_id)  # 调图 A（ainvoke）
        await asyncio.sleep(LOOP_INTERVAL_SECONDS)   # 等下一个节拍
```

它由 lifespan 注入一个 `run_diagnostic` 回调（内部 `graph.ainvoke(...)`），把"要不要诊断"
交给 monitor 节点的 `route_monitor` 条件边判断。所以：**外层是 asyncio 定时扫，内层是
LangGraph 单次诊断**——两者通过回调接口解耦。这就是"harness 驱动 agent"（第 11 章细讲）。

> **一张图记住三种循环**：
> ```
> 自主外循环(asyncio while + sleep)   →  每次触发
>     图 A(StateGraph)                →  内部条件边可 retry(图内循环)
>         analysis 节点(create_react_agent)  →  Thought/Action/Observation(ReAct 循环)
> ```

## 第 8 章 上下文工程：怎么把"喂给 LLM 的话"做到精

LLM 的上下文窗口是稀缺资源——塞太满又贵又稀释重点，塞太少又答不准。上下文工程就是
**"在有限窗口里只给最相关的信息"**。本项目做了三层：

### 8.1 检索侧：RAG 决定喂什么（已见第 5 章）

诊断/聊天时不是把整本手册塞进去，而是用 HybridRetriever 召回 top_n 相关 chunk，再经
`format_context()` 拼成带引用编号的文本。检索质量直接决定上下文质量。

### 8.2 记忆侧：只注入"此刻用得上的记忆"（见第 9 章）

`MemoryManager.build_context()` 不会把所有记忆都塞进 prompt，而是按 `subject`/`query`
匹配 + `pinned` 置顶 + 截断(120 字)。每次只挑最相关的几条长期记忆，配合最近的会话历史。

### 8.3 可追溯：让 LLM"说出处"

RAG 结果带 `citations_from()`，拼接时把来源(chunk 文档 + id)作为引用，既让 LLM 更可信，
也让前端能展示"这句话来自哪份文档"。**这是对抗幻觉的工程手段**——不是靠提示词喊
"你别编"，而是"你有据可查、我看得到你的据"。

> **老师点评**：上下文工程的三个抓手——**①体积控制**(只喂相关片段)、**②顺序与结构**
> (系统提示→相关记忆→检索片段→用户问题)、**③可引用来源**(让模型和人都能核对)。
> 不要天真地以为"上下文越多越聪明"；上下文越长，模型越容易"迷失在中间"，越贵越慢。

### 8.4 会话的滚动摘要（防窗口爆掉）

聊天多轮后历史会无限长。`MemoryManager` 的策略：`conversation_messages` 每攒 12 条就把
旧消息**压缩成一条摘要**存进线程记录，之后只带摘要 + 最近几轮原文。这样既不丢"大意"，
又控制每次注入的体积——是"无限对话不撑爆窗口"的标准做法。

## 第 9 章 四层记忆：跨会话不混乱

### 9.1 为什么需要分层

LLM/agent 天生无状态。要做"记得上次说过什么、这台设备以前啥样"，得自己存。但**不能
全塞一张表**——会话里的闲聊、诊断的历史、设备的画像、知识库的向量，性质完全不同。
本项目按"生命周期 / 用途"切成四层，各管各的，天然不混乱：

| 层 | 存什么 | 存哪 | 隔离/防乱保证 |
|---|---|---|---|
| ① 会话(短期) | 聊天多轮 role/content/ts | `conversation_threads`+`conversation_messages` | 按 thread_id 隔离；满12条滚动摘要 |
| ② 情节(事件流) | 诊断/工单/审核事件 | `agent_activity`+`diagnostics` | 只追加不改；event_type 固定 |
| ③ 画像(设备长期) | 健康轨迹/故障史/维修效果/人工反馈 | `long_term_memory`(kind=machine) | `refresh_machine_profile()` 沉淀，去重 |
| ④ 语义(知识) | 向量+文本 | Chroma + `data/index` | 只读；重建走脚本 |

### 9.2 门面 MemoryManager（`src/memory/manager.py`）

对上层暴露统一接口，屏蔽"记到哪张表"的细节：

```python
MEMORY_KINDS = ("machine", "fact", "preference", "lesson")  # 长期记忆分类白名单

# 会话层
open_thread() / append_message(role, content, ...)   # 满12条自动滚动摘要
recent_history(thread_id)                            # 取最近几轮

# 长期记忆层
remember(kind, subject, content, source)   # 校验 kind∈白名单 + 去重
recall(subject=None, query=None)           # pinned 置顶 + recency + 匹配
forget(memory_id)

# 一键组装喂给 LLM 的上下文
build_context(...)                         # 置顶 + subject/query 匹配 + 截断

# 情节 → 画像沉淀
refresh_machine_profile(machine_id)        # 从 diagnostics/维修记录 派生 machine 记忆
```

**关键工程点**：
- `remember` 里 **kind 白名单校验**——防止存进乱七八糟的类别；
- **去重 + pinned 置顶**——同样的知识不重复存，重要的记忆一直排前面；
- **画像由数据库派生沉淀**——不是让 LLM 现写，而是从真实诊断/工单记录 `refresh` 出来，
  保证画像与事实库一致、可追溯。

> **老师点评**：给学生的记忆设计口诀——**"按生命周期分层，按 thread/entity 隔离，
> 用白名单防脏，用去重防冗余，从事实库沉淀防幻觉。"**

## 第 10 章 数据层：仿真、确定性与断点续写

评委最爱问"你的数据是真的吗？怎么来的？重跑会变吗？"这一章给你标准答案。

### 10.1 数据从哪来：物理仿真器

`src/simulator/` 不是随机数造假，而是**物理退化模型 + 可控噪声**：
- `physics_models.py`：`bearing_degradation`(轴承退化)、`motor_aging`、`tool_wear`，
  用 **Paris(疲劳裂纹)、Arrhenius(温度加速)、Taylor(刀具寿命)** 等经典公式建模；
- `cnc_simulator.py`：把退化态 + 工况 → 生成 **22 维遥测**读数；
- `sensor_models.py`：`deterministic_noise()` 用**多频正弦叠加**做噪声——注意它不是
  `random`，所以**每次生成结果完全一致**（可复现）；
- `fault_injector.py`：给 6 台机器(CNC_007/018/025/036/052/078)预置渐进故障场景，
  `progression()` 把退化量从 0 平滑推到 1。

### 10.2 会不会每次重跑？

**历史数据不重跑**：67200 行(100 台×672 点，30 分钟间隔)一次性确定性生成，落
`data/zhiwei.db` 后固定，重启/重跑不变（`INSERT OR IGNORE`）。这正是"演示数据稳定"的
来源——今天演示和昨天数字对得上。

### 10.3 实时推进：数据"在往前走"

静态历史不生动。`RealtimeEngine`(`src/data/realtime.py`)让数据**随时间增量前进**：
- 每拍(默认 5 秒真实时间)把每台设备推进一个仿真步长(30 分钟)；
- 新读数的时间戳**严格大于历史最大时间戳**，只追加、不改写历史；
- `workload_for(timestamp)` 只依赖时钟推导工况：白班满负荷/夜班降载 15%、每 8h 换刀窗口、
  周三保养停机——**纯时间函数，确定性，可复现**；
- 每批写入都记 `data_provenance` 血缘：这条数据"谁、何时、什么模型算出"可追溯。

### 10.4 断点续写（本次补强的验收项）

要保证"重启后从断点续写、历史不被覆盖"，游标按三级恢复：

```
① data/sim_clock.json（持久化文件，最抗数据库被清空/迁移）
② sensor_readings 的 MAX(timestamp)（已有历史）
③ 引擎启动时刻（全新库）
```

每 tick 结束把当前时钟写回 `sim_clock.json`。`tick()` 的时间基准**永远是"上次游标+一步"**
而不是 wall-clock——保证确定性、可断点续写、任何时刻调用结果一致。实测：tick 两次后重建
引擎，时钟从文件恢复、第三次 tick 继续前进、前两次数据未被覆盖。

> **老师点评**：仿真与真实数据的边界要讲清楚——**历史=确定性仿真、实时=时钟驱动追加、
> 血缘=每行可溯源**。这是你答辩时"数据真实感"的三张底牌。

## 第 11 章 MCP 与 Harness：两个"高级词"到底是什么

### 11.1 先说实话：本项目没有 MCP、也没有第三方 harness

这章我要先纠正一个可能的误解。**本项目没有接入 MCP（Model Context Protocol），也没有
套用任何现成的 agent harness 框架。** 那"harness 工程怎么实现的"怎么答？答案在下面。

### 11.2 那"harness"在项目里是什么？—— 进程内的执行外壳

Harness(马具/执行外壳)泛指"把 agent 跑起来的运行时环境"：负责装配模型、工具、记忆，
驱动 agent 循环，处理事件与外部交互。本项目没引第三方 harness，是因为**FastAPI 应用本身
就是 harness**——它由三块组成：

| harness 部件 | 本项目实现 | 作用 |
|---|---|---|
| **模型装配** | `UnifiedLLMClient` + `AGENT_ROUTING` | 提供/路由模型 |
| **工具装配** | `SkillRegistry.discover()` + 图节点 | 提供能力给 agent |
| **循环驱动** | `AutonomousLoop` + `ActivityBus` + lifespan | 定时扫设备、推进数据、广播事件 |
| **外部接口** | FastAPI 50 端点 + 2 WebSocket | 人类/前端接入 agent |

生命周期在 `src/api/main.py::lifespan`：`bootstrap_database → FaultGraph → 编译图A →
ActivityBus → 按环境变量起 AutonomousLoop/RealtimeEngine → SkillRegistry.discover →
装配聊天 Agent`。`app.state.graph` 持有图 A 编译实例，"智能体运行时"作为应用状态存活。
`AutonomousLoop` 用 asyncio `while not stop_event` 做节拍，通过注入的 `run_diagnostic`
回调去 `ainvoke` 图 A——**这就是"harness 驱动 agent"**。

> 一句话理解：**当你不引框架时，你自己写的"装配 + 循环 + 事件 + 接口"就是你的 harness。**
> 本项目把它朴素地落在了 FastAPI 里，够用且好懂——正好当教学范本。

### 11.3 什么是 MCP，本项目为何没用、将来怎么接

**MCP(Model Context Protocol)** 是 Anthropic 推的**开放协议**，目标是让"任意 LLM 应用"和
"任意工具/数据源"能即插即用，类似"AI 界的 USB-C"。它定义了三种角色：
- **Host(宿主)**：如 Claude Desktop / 你的 agent 应用，发起请求；
- **Client**：宿主里的连接器，负责跟 server 通信；
- **Server**：暴露工具/资源/提示词的一方(比如你的 skills)。

协议走 **JSON-RPC 2.0**，核心是工具发现与调用：host 问 `tools/list`，server 回工具清单
(名称+描述+JSON Schema 入参)；host 决定用哪个后发 `tools/call`。

**为什么本项目不需要它**：因为当前宿主就是**本项目自己的 FastAPI + 前端**，工具(skills)
直接在同一进程里被 `SkillRegistry` 发现和调用，不需要跨进程/跨应用的"标准插头"。你把
skills 当"本机函数"用，MCP 是把它们变成"可被任何外部宿主调用的标准服务"。

**将来怎么接(可当"展望"讲给评委)**：用 `fastmcp` 把每个 skill 包成工具，起一个 MCP
server，让 Claude Desktop 等外部宿主能 `tools/list`/`tools/call` 调它——本质是把现在
`/api/skills` 的 REST 契约翻译成 MCP 的 JSON-RPC 发现协议：

```python
# 未来演进示意（非本项目现有代码）
from mcp.server.fastmcp import FastMCP
mcp = FastMCP("zhiwei-skills")
@mcp.tool()
def rul_weibull(machine_id: str) -> dict:
    return SkillRegistry.run("rul_weibull", {"machine_id": machine_id})
mcp.run()   # 外部宿主即可按标准协议调用
```

> **老师点评**：答辩若被问"MCP"，分三步答：①MCP 是"AI 工具即插即用的开放协议/USB-C"；
> ②本项目内部已用注册表实现等价能力，只是作用域是本进程；③外部互通时可加一层 MCP
> server 桥接——**协议是工程选择，不是必需**。诚实 + 有前瞻，比硬吹更得分。

### 12.1 一条完整的业务闭环（你能讲给任何人的故事）

```
① AutonomousLoop 每 30s 扫设备
② monitor 节点看 22 维遥测 → 判定 CNC_036 异常(is_anomaly=True)
③ route_monitor 条件边 → 进 diagnostic
④ diagnostic 节点 → 确诊"主轴轴承磨损"(fault_code=1)，严重度=high
⑤ knowledge 节点 → RAG 检索同故障码的 SOP/案例做对证
⑥ prediction 节点 → rul_weibull 威布尔 → RUL P10/P50/P90
⑦ decision 节点 → 分级处置建议
⑧ report 节点 → 拼装诊断报告
⑨ reflection 节点 → 自检报告质量；不过则 retry(最多3次)
⑩ 落库 agent_activity + diagnostics(情节记忆) + 更新设备画像
⑪ 创建通知(待审) → 前端徽标+1
⑫ 管理员点"批准"(high) → 后端 review_notification
     └→ SkillRegistry.run("maintenance_report", {...})   # 审批联动
     └→ 生成 RPT-xxx 报告落 maintenance_reports → 通知卡片变"查看报告"
```

每步都留痕(trace_id / tool_calls / provenance)，可回放——这是"可追溯"的完整体现。

### 12.2 十个"易错点/考点"速记（老师划重点）

1. **反思循环 ≠ ReAct**：图外层是固定图+条件边+计数，ReAct 只藏在 analysis 节点里。
2. **skills 体系 ≠ analysis 的本地 @tool**：前者注册表化、函数级+注册表级调用；后者喂
   ReAct。`as_langchain_tools()` 定义了但没被调用(可当演进点讲)。
3. **MemorySaver 只是进程内存**：重启即失；长期记忆在 SQLite 表。
4. **没有 sim_clock 会怎样**：断点靠 DB MAX(timestamp)；补了 `data/sim_clock.json` 文件
   做最稳的那一级。
5. **RAG 没有 knowledge_chunks 表**：chunk 持久化在 `data/index/` + Chroma，不是 SQLite。
6. **RRF 为什么不用分数加权**：BM25 无界 vs 向量∈[-1,1] 量纲不可比，RRF 只看排名。
7. **降级链多层**：DeepSeek 缺 key→本地；LLM 增强默认关；聊天 LLM 挂→模板兜底；Ollama
   挂→纯 BM25。演示永不白屏。
8. **温度与用途**：判断/自检用低温(0.0~0.1)，生成/问答才稍高。
9. **上下文要精不要长**：滚动摘要 + 只注入相关记忆/检索片段 + 可引用来源。
10. **历史数据确定性生成、实时只追加**：数据真实感来自物理退化模型 + 可复现噪声 + 血缘。
